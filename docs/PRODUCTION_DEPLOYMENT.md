# CYBEROS production deployment

This is the active deployment guide. The older phase-by-phase notes in
DEPLOYMENT.md are historical and do not describe the current production
bootstrap or session architecture.

## Recommended topology

Run the Go API as a long-lived container/process with PostgreSQL. The API owns
authentication, authorization, grants, broker execution, durable audit, event
persistence and worker identity. Do not deploy the Go API as a Vercel serverless
function: it uses a long-running HTTP server and supports SSE.

The React console can be deployed independently to Vercel:

- app.example.com — Vercel frontend
- api.example.com — long-running CYBEROS API/container
- PostgreSQL — managed, private network if available

Use sibling subdomains on the same registrable domain. The browser session cookie
uses SameSite=Strict; separate-site frontend/API domains will not send that
cookie even when CORS is configured.

## Vercel frontend

Create a Vercel project with:

| Setting | Value |
|---|---|
| Root Directory | frontend |
| Framework Preset | Vite |
| Install Command | npm ci |
| Build Command | npm run build |
| Output Directory | dist |
| Node.js | 22.x or 24.x |

frontend/vercel.json provides the React Router SPA fallback. Add these
build-time variables to the Vercel project:

    VITE_CYBEROS_API_MODE=live
    VITE_CYBEROS_API_BASE=https://api.example.com

VITE_CYBEROS_API_BASE is public configuration, not a secret. Never place API
keys, signing keys, database credentials or private certificates in Vite
variables. Redeploy after changing build-time variables.

On the API service configure:

    CYBEROS_ALLOWED_ORIGINS=https://app.example.com
    CYBEROS_COOKIE_SECURE=true

The API returns a credentialed CORS response only for the exact allow-listed
origin. Keep HTTPS enabled on both hostnames.

## Container build and run

Build the image from the repository root:

    docker build -t cyberos:production .

The image builds the Vite console and embeds it in the Go binary. The build uses Go 1.27.3 and the runtime image uses Alpine 3.24.4. The runtime
image contains the application, migration SQL files and CA trust bundle, runs
as non-root UID 10001, and exposes port 8080.

Required production environment:

    CYBEROS_ENV=production
    CYBEROS_API_ADDR=:8080
    CYBEROS_DATABASE_URL=postgres://cyberos_app:REDACTED@db.example.internal:5432/cyberos?sslmode=verify-full&sslrootcert=/run/secrets/postgres-ca.pem
    CYBEROS_GRANT_SIGNING_KEY=<64 hex characters generated by a secret manager>
    CYBEROS_BOOTSTRAP_API_KEY=<pre-generated cos_ key>
    CYBEROS_AUTH_REQUIRED=true
    CYBEROS_SESSION_BACKEND=postgres
    CYBEROS_COOKIE_SECURE=true
    CYBEROS_SESSION_TTL=12h
    CYBEROS_SESSION_IDLE=30m
    CYBEROS_ALLOWED_ORIGINS=https://app.example.com

Generate independent secrets; do not reuse the database password as the grant
signing key or bootstrap API key:

    openssl rand -hex 32
    printf 'cos_%s\n' "$(openssl rand -hex 32)"

Supply the PostgreSQL CA file as a mounted secret at the path in sslrootcert.
sslmode=verify-full checks both the CA chain and database host name. Use a
dedicated database role with only the schema/table privileges the application
requires. Migrations currently run during application startup, so the
configured role must also have the required migration privileges.

On first startup, CYBEROS creates the active bootstrap principal. A fresh
database must receive CYBEROS_BOOTSTRAP_API_KEY; the application deliberately
refuses to generate and print a production key into container logs. If a
pre-provisioned active operator key already exists, the bootstrap variable can
be omitted. Keep the operator secret in a secret manager and rotate it after
initial tenant/API-key provisioning.

The /api/v1/health endpoint is liveness. /api/v1/ready checks the PostgreSQL
connection and is suitable for the container/orchestrator readiness probe.

## API-key provisioning

Use the bootstrap operator API key in an Authorization header. Create a
tenant-scoped credential for an already-created active principal:

    curl --fail-with-body https://api.example.com/api/v1/auth/keys \
      -H "Authorization: Bearer $CYBEROS_BOOTSTRAP_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{
        "principal_id": "principal-123",
        "tenant_id": "tenant-123",
        "role": "admin",
        "ttl_seconds": 2592000
      }'

The returned api_key is displayed once. Store it securely immediately. Roles
supported by the provisioning endpoint are viewer, analyst and admin. It
deliberately does not mint additional platform operator credentials.
Revoke a compromised key with:

    curl --fail-with-body -X POST \
      "https://api.example.com/api/v1/auth/keys/<key-id>/revoke" \
      -H "Authorization: Bearer $CYBEROS_BOOTSTRAP_API_KEY"

Revocation also invalidates existing browser sessions for that key. Issuance and
revocation are written to the durable audit log.

## Grant and supply-chain trust administration

All routes in this section require the platform bootstrap/operator credential;
tenant administrators cannot change global trust or revoke grants owned by
another tenant.

Revoke a grant that has not started executing:

    curl --fail-with-body -X POST \
      "https://api.example.com/api/v1/grants/<grant-id>/revoke" \
      -H "Authorization: Bearer $CYBEROS_BOOTSTRAP_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{"reason":"operator cancelled before execution"}'

Grant revocation is durable and idempotent. A grant already CLAIMED is not
revocable because its execution outcome is uncertain; investigate the target
and execution record rather than trying to cancel or replay it.

Trust a reviewed pack digest for a project:

    curl --fail-with-body https://api.example.com/api/v1/trust/packs/trust \
      -H "Authorization: Bearer $CYBEROS_BOOTSTRAP_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{"project_id":"project-123","digest":"sha256:<64-lowercase-hex>","reason":"reviewed pack"}'

Inspect or revoke a digest with `GET /api/v1/trust/packs?project_id=...&digest=...`
and `POST /api/v1/trust/packs/revoke` (include a reason). Signer registration,
inspection, disable and revoke are available at
`/api/v1/trust/signers` and `/api/v1/trust/signers/{key-id}`. Signer public keys
must be base64-encoded Ed25519 public-key material. Every mutation writes a
durable audit record; if audit persistence fails the API returns an error and
the operator must inspect the actual trust state before retrying.

## Worker mTLS

Worker identity is separate from human/browser authentication. Register a worker
with its SHA-256 certificate fingerprint, then activate it through the
/activate route. The heartbeat route bypasses human API-key middleware only
because it requires a verified client certificate and binds that fingerprint to
the registered project/worker identity.

For direct HTTPS termination in the Go process, mount the controller certificate,
private key and worker CA, then set:

    CYBEROS_TLS_CERT_FILE=/run/secrets/controller.crt
    CYBEROS_TLS_KEY_FILE=/run/secrets/controller.key
    CYBEROS_WORKER_CA_CERT_FILE=/run/secrets/worker-ca.crt

The listener uses TLS 1.3 and verifies client certificates when supplied;
ordinary browser requests may omit them. Worker heartbeat requests may not.
When TLS terminates at an external reverse proxy, this process does not receive
the verified client certificate, so the mTLS heartbeat route remains unavailable
unless the worker connection terminates TLS directly at CYBEROS. Do not forward
an unverified certificate identity in a client-controlled HTTP header.

## External tool execution

Production no longer registers mock or stub executors. Real adapters are present,
but process execution remains disabled by default. Enable it only with a
deliberate binary allow-list:

    CYBEROS_PROCESS_ENABLED=true
    CYBEROS_PROCESS_ALLOW_SHELL=false
    CYBEROS_PROCESS_ALLOWED_BINS=nmap,curl
    CYBEROS_PROCESS_TIMEOUT=60s
    CYBEROS_PROCESS_MAX_OUTPUT_BYTES=262144

Add python3 or rustc only when those runtimes are required. The process runner
never invokes a shell. Production grants must include an explicit executor hint;
generic grants are not silently routed to an arbitrary adapter. Ensure the
binaries are installed in the runtime image and that the allowed paths match
the paths resolved inside that image.

## Migration and operational notes

- Startup applies all SQL files in migrations/ in lexical order, currently
  through 025_durable_auth_sessions.sql.
- PostgreSQL persists API keys, sessions, audit entries, cases, workers,
  assignments and grant lifecycle state.
- Sessions are shared across instances and checked against the live API-key
  row; revocation or expiry invalidates existing sessions.
- SSE fan-out, login rate limiting, and AI/autonomy rate-limit buckets are
  currently process-local. Run one API replica until shared pub/sub and
  distributed rate-limiting are configured; PostgreSQL durability alone does
  not make those facilities cross-replica.
- A grant left in CLAIMED after a process crash is an uncertain execution,
  not permission to retry. Investigate the host/target before any manual
  recovery. Do not delete or automatically re-run an in-flight grant.
- Keep PostgreSQL backups and periodically test restore. Restrict access to
  audit data and retain it according to the incident-response requirements.
- Set reverse-proxy request size/time limits to match the API's 1 MiB body
  limit. Preserve the original host and the exact HTTPS Origin.

## Verification before public traffic

    go test ./...
    go vet ./...
    cd frontend
    npm test
    npm run typecheck
    npm run lint
    npm run build

Then verify against a disposable PostgreSQL database with the same SSL
verification mode as production, exercise first-start bootstrap, key issue and
revocation, login/logout, tenant isolation, worker certificate rejection and
acceptance, audit pagination, readiness failure, SSE and one controlled tool
execution. Do not treat unit tests without PostgreSQL as proof that migrations
or durable repositories work.
